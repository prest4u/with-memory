# 发布流程与 GA 门禁

所有外部门禁通过前，源码版本必须保持在 1.0 以下。本地测试通过是必要条件，但不能替代签名凭据、干净 OS 安装、真实 harness 环境和独立审阅。

## CI

`.github/workflows/ci.yml` 在 macOS arm64/x86_64、Windows x86_64、Linux x86_64 上运行 Python 3.10/3.12，门禁包括 Ruff、strict mypy、单元/集成测试、总体分支覆盖率、事务/迁移/权限模块 95% 分支覆盖率、双语检索质量、合成性能、依赖审计、secret scan、SBOM，以及每周/手动 10 万事实 + 10 万文件参考基准。

## 冻结发布工作流

`.github/workflows/release.yml` 只能手动触发，并绑定已有 `vVERSION` tag 与完整 source commit。自动检查覆盖源代码身份、基准结果和以下人工声明；声明对应的实际材料由发布审阅者另行核对：

- `pyproject.toml`、`eric_memory.__version__`、tag、commit 与内置 Ed25519 公钥完全一致；
- `release/evidence.json` 记录 owner 声明的 Codex、Claude Code、Cursor、Hermes、Kimi、Qwen 的真实端到端通过；
- owner 声明安全、迁移、隐私、发行由四名不同 reviewer 审阅同一 commit；
- owner 声明对真实库完成只读迁移计划与已验证备份，且未修改真实库；
- owner 声明官方 MCP conformance runner 对实际发行的 stdio server 跑过 active server suite，并保存测试结果及哈希；
- 10 万规模基准和全部正确性/安全门禁通过。

示例使用无效占位符。替换后可能通过格式检查，声明的真实性仍需人工确认。

`verify_release_evidence.py` 只校验 owner 人工声明的字段、哈希格式及版本与 commit 引用，不读取原始报告、不重新计算报告哈希、不验证审阅者身份，也不执行声明中的测试。受保护发布 job 的指定审阅者必须在批准前查看原始材料、重新计算哈希、核对审阅者身份和 commit 批准记录，并检查真实客户端、迁移和 conformance 结果。私有报告应保存在公开仓库之外。当前自动化单独运行无法确认 GA 条件全部满足。

## 原生产物

PyInstaller 必须在每个目标 OS 分别构建，`package_release.py` 会拒绝交叉打包。每个平台冻结候选都用纯合成临时数据跑 `init → candidate → review → search → backup → restore → doctor → support-bundle → MCP`，并门禁首次/稳态 CLI 启动与 MCP 初始化。

macOS 要求 Developer ID 签名与公证；Windows 要求 Authenticode 与时间戳验证。四个 archive 统一受 Ed25519 签名清单保护，并附 SHA-256、CycloneDX SBOM 与 GitHub provenance。原生签名、公证和最终清单签名、发布两个阶段都使用 `production-release` environment。需在该 environment 配置必需审阅者及允许发布的 ref，并将所有签名与公证凭据保存为 environment secrets；各 job 获批后才能读取凭据。工作流只使用已有 tag，不会静默创建。

## MCP conformance

With. 锁定官方 MCP Python SDK v2，并用官方 SDK client 验证真实 stdio 服务、严格工具 JSON Schema、畸形 JSON-RPC、legacy 协商、最小权限发现和冻结二进制。官方 conformance runner 当前只接受 HTTP URL 来测试 server；stdio server 支持仍是[上游开放需求](https://github.com/modelcontextprotocol/conformance/issues/258)。v1 明确不发布 HTTP listener，因此在上游支持 stdio 前，官方 server suite 仍无法完成 GA 要求的实际验证。`verify_release_evidence.py` 会强制要求真实 `stdio`/`shipping-server` 通过，随附示例将该结果标为 blocked；HTTP 或 SDK fixture 结果不能冒充产品 conformance。

## 发布顺序

1. 标记并构建 `1.0.0-rc.1`，只迁移合成库与副本。
2. 经 owner 明确同意，对真实库运行只读迁移计划并创建/验证完整备份。
3. 冻结 commit 与验证记录，完成全部独立审阅。
4. 构建、签名、公证、attest 并检查四个平台不可变候选。
5. 发布 RC，在干净用户与六类真实 harness 上验收。
6. 对 `1.0.0` 重复冻结流程。数据损坏、越权、迁移不一致、未签名、验证记录缺失或核心 harness 失败都会阻断 GA。

任何工作流都不会因为仓库被编辑就迁移 owner 的真实数据库或自动发布。
