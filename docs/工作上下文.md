# With. 工作上下文

With. 现在可以将获准的日志和文档暂存在本地，再按问题返回相关片段。这个模块使用现有 Python、SQLite 和 MCP 服务，无需安装 Context Mode 或 Node。

原有长期记忆继续使用 `memory.db`。临时资料单独保存在 `context/working.sqlite3`，不会进入事实导出、With. 管理的备份、支持包或 Obsidian 投影。安装升级不会自动开启临时原文存储。

## 启用一个项目

下列命令使用已经安装好的 `eric-memory`。源码运行时，将其替换为专用虚拟环境中的 Python 绝对路径及 `bin/eric-memory` 绝对路径。先用一个软件项目的输出目录试用，路径必须真实存在。

```sh
eric-memory --data-dir /ABS/data harness add --key codex --name Codex
eric-memory --data-dir /ABS/data source approve /ABS/project/captured --harness codex
```

从输出读取 `source_uid`，替换下面的 `SOURCE_UUID`。允许读取来源元数据与允许暂存原文是两个独立设置：

```sh
eric-memory --data-dir /ABS/data context enable --project demo --source-uid SOURCE_UUID --allow-content-storage
eric-memory --data-dir /ABS/data harness grant --key codex --capability context:read --scope-kind project --scope-key demo
eric-memory --data-dir /ABS/data harness grant --key codex --capability context:write --scope-kind project --scope-key demo
```

如果还需要在统一检索中返回该项目的长期事实，增加对应读取授权：

```sh
eric-memory --data-dir /ABS/data harness grant --key codex --capability fact:search --scope-kind project --scope-key demo
```

重启客户端，让它重新发现工具。沿用原来的 With. MCP 配置及 `--principal codex`，无需增加第二个服务器。

## 实际使用

让客户端原有的命令执行工具把大型输出写入获准目录中的文件，并单独报告命令退出状态。接着调用 `memory_context_index`：

```json
{"project":"demo","source_uid":"SOURCE_UUID","source_locator":"build.log","label":"构建输出"}
```

模型收到文档 ID、内容哈希、索引规模和过期时间，不会在这一步收到整份日志。`source_locator` 使用相对路径与正斜杠，Windows 也相同。可以传入 `expected_sha256`，要求实际文件与预期快照一致。

之后调用 `memory_recall`：

```json
{"project":"demo","query":"compiler error","max_bytes":8192}
```

它返回相关事实及临时片段，注明来源、状态和行号。如果当前客户端没有该项目的事实读取授权，`facts_access` 为 false，仍可返回获准的临时资料。跨项目的长期偏好继续用原有 `memory_search`。

需要精确内容时，调用 `memory_context_read`，传入 `project`、`artifact_uid` 和 `start_line`。按返回的 `next_line`、`next_column` 继续读取；这也适用于超长 JSON 单行和中文文本。列号按 Unicode 字符计数，从 1 开始。两个值为 null 表示已读到末尾。

`max_bytes` 限制紧凑 UTF-8 JSON 结果的字节数，默认 8192，允许 2048–32768。MCP 的封装及文本／结构化两种表示还会增加传输量。字节数不能直接作为模型计费 token 数。

支持执行命令但没有 MCP 的客户端可以使用同一内核：

```sh
eric-memory --data-dir /ABS/data context index --principal codex --project demo --source-uid SOURCE_UUID --source-locator build.log
eric-memory --data-dir /ABS/data context recall --principal codex --project demo "compiler error"
```

只有在大段输出进入模型之前进行文件捕获，才能减少这部分上下文占用。先让模型读完整段输出，再索引它，无法撤回已经占用的输入。当前版本提供显式捕获和检索流程，不会自动安装 hooks 或截获所有工具。

## 在多个客户端间使用

Codex、Cursor、Kimi、Claude、Hermes、Qwen、Grok 和自定义客户端都使用同一套 With. 接口。模块不根据客户端名称采用不同存储逻辑。

把某个项目的 `context:read` 授予第二个客户端，就允许它检索该项目启用的临时资料。这样可以由 Codex 写入，Cursor 接着读取。写入仍要求来源归当前客户端所有；仅有项目写入授权，不能读取其他客户端拥有的来源文件。

多个客户端需要各自写入时，分别批准它们的输出目录，再把这些来源启用到同一个项目。共享读取无需重新指定原有来源的所有者。重新批准来源会产生新的同意记录，之前的临时快照会失效。

客户端配置参考现有 [通用 MCP 文档](../adapters/generic-mcp.md)。只有远程聊天功能、无法访问本地 stdio 或文件系统的产品，需要额外接入方式；这个版本没有增加 HTTP 服务。

任务恢复可以使用获准目录中的简短进度文件：压缩会话前索引该文件，恢复后检索并检查当前源文件。模块不自动收集完整会话，也不会自动把临时内容变为长期事实。

## 保存、清理与撤销

- 默认保留 7 天，启用时可用 `--ttl-days` 设置为 1–30 天。到期立即停止返回内容；索引新文件或运行 `context clean` 时清理过期缓存。没有后台清理进程。
- 单文件最多 5 MiB，每个项目最多 1000 份文档、50 MiB 原文和 100 个启用来源。SQLite 索引会额外占用磁盘空间。
- 文件需要是稳定的 UTF-8 普通文件。路径穿越、隐藏文件、符号链接、重解析点、硬链接、超限文件和捕获时发生变化的文件会被拒绝。
- 凭据、未成年人个体信息和可识别的完整会话导出仍会被内容检查拒绝。检查不能保证任意文件都不含敏感内容，启用时仍应选择明确的来源目录。
- 每次查询重新检查授权、来源状态及同意记录。撤销来源后，后续查询不再返回旧内容；已经进入客户端对话的文本无法由 With. 撤回。
- 再次索引同一路径会生成新的文档 ID。过期或已替换的 ID 返回 `NOT_FOUND`，需要重新索引当前文件。读取操作不会自动刷新快照或延长保留时间。
- 临时资料始终作为未经审核的参考内容。需要长期保留时，用现有 `memory_candidate_add` 提交短候选，再进行本地审核。

查看状态：`context status --principal KEY --project demo`。本地管理员运行 `context clean` 只清理过期资料。关闭项目临时存储并删除对应缓存：

```sh
eric-memory --data-dir /ABS/data context disable --project demo --confirm
```

再撤销该项目的 `context:read`／`context:write` 授权，重启客户端即可移除新增工具。长期记忆保留。清理使用 SQLite secure-delete 和 DELETE journal；原始文件、系统快照及用户自行制作的外部备份需要单独管理。

只移除一个来源时，增加 `--source-uid SOURCE_UUID`；空值或无效 UUID 会被拒绝。临时库损坏或属于另一个资料库时，本地管理员可运行 `context reset --confirm`。它删除所有项目的临时正文、来源启用记录及 SQLite 附属文件，长期事实保留。之后需要重新启用选定来源。当前版本通过文件锁协调读取与重置；升级前应停止旧版客户端。

恢复主库备份或执行紧急清除时，会先移除整个临时库。这样旧的来源同意记录无法让失效快照恢复可读，紧急清除也不会留下临时正文副本。清理失败则停止后续主库操作；紧急清除的预览会显示这一影响。来源撤销后的缓存清理如果失败，结果会明确返回 `committed: true`、`context_cleanup: pending` 和警告；此时来源访问已经撤销，可重试撤销或运行本地重置。

## 当前验证范围

新增测试通过官方 MCP SDK 启动 With. 的实际 stdio 服务，使用八种客户端身份完成工具发现、索引、检索和读取，并检查重启后的行为。这验证的是协议及身份处理，不能据此声称八个客户端应用都已实测。

2026-09-08，本机 macOS 上的 Cursor CLI 通过项目 MCP 配置成功加载安装包，并发现全部三个新工具。安装包也从源码目录之外完成 CLI、stdio 索引、检索、精确读取及重启测试。Cursor 模型在实际任务中是否持续选择这些工具，以及其他客户端应用的完整流程，仍需继续实测。

测试也包含中英文片段、精确翻页、路径含空格、授权撤销、来源变化、并发、过期和被拒绝的输入。现有 CI 已配置 Python 3.10／3.12，以及 Linux、Windows、macOS arm64／x86_64；只有真正完成的 CI 运行才能确认相应系统结果。公开发布仍需完成仓库原有的签名、客户端实测及独立审查要求。
